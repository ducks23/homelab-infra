Build log

What actually happened, in order — including the parts that didn't work the first time.

  1. Scaffolded the Ansible project

    Built k3s-cluster/ from scratch: ansible.cfg, an inventory, and four roles (k3s_common, k3s_server, k3s_agent, kube_vip) sequenced by site.yml. Topology was a deliberate choice going in: all 3 nodes as k3s server nodes with embedded etcd, not 1 master + 2 workers — so the cluster tolerates any single node dying.

  2. Wired up SSH key auth

    Generated no new key — reused the existing ~/.ssh/id_ed25519 and pushed it to all three boxes with ssh-copy-id, since Ansible needs non-interactive login to run unattended.

  3. Installed Ansible locally

    brew install ansible on the Mac, then ansible-galaxy collection install -r requirements.yml for community.general and ansible.posix. Both playbooks passed --syntax-check before touching real hardware.

  4. Pointed the inventory at real hardware

    Swapped the placeholder IPs for the actual LAN addresses — 192.168.1.250, .216, .135 — all under one ansible_user=ubuntu.

  5. Picked the VIP against the real DHCP range

    Checked the UniFi console (Settings → Networks → DHCP Range) to confirm 192.168.1.3 sits outside the address pool the router actually hands out — a floating IP that DHCP could also assign to some other device is a conflict waiting to happen.

  6. First live run — blocked on sudo

    Ran ansible k3s_cluster -m ping: SSH worked, but every host failed with "Missing sudo password." Passwordless sudo hadn't been set up yet. Fixed with ssh -t (a plain ssh 'cmd' has no pty, so sudo can't prompt) to drop ubuntu ALL=(ALL) NOPASSWD:ALL into /etc/sudoers.d/ubuntu on each box.

  7. Pre-flight-checked the NIC name

    kube-vip needs the real network interface to send ARP on, and eth0 was only a guess. An ad-hoc ansible -m shell -a "ip -o -4 route show to default" confirmed all three run ens18 (Proxmox-style VM naming) — updated kube_vip_interface before deploying.

  8. Generated a real join token

    Replaced the placeholder k3s_token with a genuine openssl rand -hex 32 value directly in group_vars/all.yml — the shared secret every node needs to join the etcd cluster.

  9. Deployed — hit two real bugs

    k3s installed and all three nodes joined cleanly, but the playbook itself failed at the last step for two reasons: stdout_callback = yaml in ansible.cfg referenced a community.general plugin removed in v12+, and the play-level become: true leaked into the delegate_to: localhost tasks that write the kubeconfig to the Mac, trying to sudo on a machine that had no idea what that meant. Fixed both fixed — result_format: yaml is the modern equivalent, and the two local tasks now carry an explicit become: false.

  10. Re-ran clean, verified end to end

    kubectl get nodes showed all three Ready with control-plane,etcd roles. A raw curl -sk https://192.168.1.3:6443/livez came back 401 Unauthorized — the correct answer from an unauthenticated request, and proof the floating address was already alive and routing to a real API server.

How the floating IP works

The mechanism behind 192.168.1.3, end to end.

The problem it solves

Embedded etcd already makes the control plane survive a node dying — two of three etcd members is still quorum. But nothing about that gives clients a stable place to point. A kubeconfig hardcoded to 192.168.1.250 breaks the moment that specific box reboots, even though the other two nodes are perfectly capable of answering API requests. kube-vip closes that gap: one address, 192.168.1.3:6443, that always resolves to whichever node is currently healthy.

Two mechanisms, one DaemonSet

kube-vip runs as an ordinary DaemonSet — one pod per control-plane node, scheduled via the node-role.kubernetes.io/control-plane node affinity in roles/kube_vip/templates/kube-vip-daemonset.yaml.j2. Two things happen inside it:

1 · Leader election

All three pods race for a Kubernetes Lease object in kube-system (the same primitive controller-manager and scheduler use for their own HA). Whoever holds it is the leader. The RBAC applied alongside the DaemonSet grants exactly the get/list/watch/update verbs on leases that this requires.

2 · ARP announcement

The leader pod runs with hostNetwork: true plus NET_ADMIN/NET_RAW, binds 192.168.1.3 straight onto its node's ens18, and fires a gratuitous ARP broadcast: "this address now lives at my MAC." Every switch and host on the segment updates its ARP table on the spot.

This is Layer 2 / ARP mode — one of two modes kube-vip supports. The other, BGP mode, needs a router that peers over BGP with each node; that's a datacenter pattern, not something a UniFi gateway does. ARP mode asks nothing of the router at all — it only needs all three nodes on one broadcast domain, which a home LAN already is. The trade-off: it's active/standby, not load-balanced. One node answers :6443 at a time; the other two are cold spares for the address, not extra capacity for it.

What's actually in the manifest

The rendered DaemonSet (roles/kube_vip/templates/kube-vip-daemonset.yaml.j2) boils down to these env vars on the kube-vip container:

vip_arp "true" # Layer 2 / ARP mode, not BGP cp_enable "true" # announcing the control-plane, not a Service address "192.168.1.3" port "6443" vip_interface "ens18" # confirmed via pre-flight check, step 7 vip_leaderelection "true" vip_leaseduration "5" # seconds before a dead leader's lease expires vip_renewdeadline "3" # seconds between renewals

The chicken-and-egg it has to route around

kube-vip is itself a workload — it needs a running API server to be scheduled onto in the first place, which means it can't be the thing node2 and node3 use to join the cluster. That's why k3s_server joins them straight to node1's real address, 192.168.1.250:6443, and the kube_vip role only runs afterward, applying the DaemonSet from node1 via k3s's bundled kubectl. Only once all three are up does 192.168.1.3 become the address anything else — your local kubeconfig included — actually uses.

One knock-on effect: every node's install command carries --tls-san 192.168.1.3 alongside its own IP. Without that, the API server's TLS certificate simply wouldn't cover the VIP, and kubectl would reject the connection as an unrecognized host the moment you pointed it at the floating address.

Worth knowing

ARP mode only fails over the address — it doesn't load-balance across the three nodes, and it only covers the API server. Ordinary LoadBalancer traffic for your own workloads is a separate problem; that's exactly why servicelb was disabled in k3s_server_disable going in, leaving room for MetalLB (or a second kube-vip instance in Service mode) later if you need it.
